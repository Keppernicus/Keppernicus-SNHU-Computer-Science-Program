### Architecture

I ended up using two pretty different approaches to the front end on this project. The customer-facing site is server-rendered. Express takes the request, a controller grabs the data, and Handlebars turns it into HTML before it ever gets to the browser. Early on those pages were just static HTML with the content hardcoded in. I converted them to templates with shared header and footer partials, and later moved the data behind them off a JSON file on disk and onto a fetch call against the API. The browser doesn't do much in this setup, it just gets finshed HTML and displays it.

The admin side is an Angular single page application, which works the opposite way. The browser downloads the app once and after that the components handle routing, rendering, and state on their own, only asking the server for JSON when they need it. Moving between the trip listing and the edit form never reloads the page. The tradeoff is a bigger initial download and a lot more logic running in the browser, and you get a much faster, more interactive experience after that first load. I think the split makes sense for this application. The customer pages benefit from loading fast and staying simple, and the admin site benefits from being responsive since an administrator is going to be working in it continuously.

MongoDB made sense for the back end because the data fits a document model. A trip is self-contained, code, name, length, start date, resort, price, image, description, with nothing that needs joining across tables. Storing each trip as one document means the API can hand it back as JSON without translating anything. Mongoose adds a schema on top of that, so you still get type checking, required fields, and unique constraints without giving up the flexibility. It also just fits the rest of the stack. The whole thing runs on JavaScript, and documents are already close to JavaScript objects, so the data doesn't have to change shape as it moves through the layers.

### Functionality

JSON and JavaScript are related but they aren't the same thing. JavaScript is a programming language. JSON is a text format for data that borrows JavaScript's object syntax, but it's much more limited, it only holds strings, numbers, booleans, null, arrays, and objects. No functions, no variables, no comments, and the keys have to be quoted. That limitation is the point though since it's just plain text with a strict structure, any language can read it.

In this project JSON ties everything together. The trip data starts as JSON in trips.json and the seed script loads it into MongoDB. Mongo stores it as BSON, which is a binary version of the same structure. Mongoose hands it back to the controllers as JavaScript objects, and res.json() turns it back into JSON for the response. The Angular service picks that up and maps it onto the Trip interface, and the components render it. The same data crosses four boundaries and keeps its shape the whole way through.

I refactored a fair amount as the project went on. The static HTML pages became Handlebars templates with shared partials, so a change to the header only had to happen once instead of on every page. The customer travel page originally read trips.json off the disk when the server started, and I rewrote it to fetch from the API instead, so now a trip added through the admin site shows up on the public site without restarting anything. On the Angular side I pulled the trip display markup out of the listing component and made it its own trip card component that takes a trip through an @Input and emits an event when you hit its delete button. The listing doesn't need to know how a trip gets displayed anymore, and the card doesn't need to know where trips come from. I did the same thing with authentication, instead of adding the token to every API call by hand, an HTTP interceptor attaches it to every outgoing request in one spot. That's the real benefit of reusable components, you cut down duplicate code and changes stay in one place, and each piece is easier to think about because it only does one thing.

### Testing

An endpoint is a specific URL the API exposes, and the method is the HTTP verb that says what you're doing with it. The same path does different things depending on the verb. GET /api/trips returns the whole collection while POST /api/trips creates a new one, and GET /api/trips/:tripCode returns a single trip while PUT replaces it and DELETE removes it. Express routes map each verb on each path to a controller function, so it's the pairing of the two that decides what actually runs.

Testing them should include more than just making sure data comes back. Each endpoint needs testing for successes and failures, asking for a trip code that doesn't exist should give 404, and a trip that's missing a required field or duplicates an existing code should give 400 rather than a server error. I used Postman for this since it'll send any verb with any body and shows you the status code and the response directly without the front end involved at all. Testing the API separately from the SPA is also important because when something breaks it tells you right away whether the problem is on the server or the client.

Security adds a layer have to test separately as well. Once I added authenticateJWT to the create, update, and delete routes, those endpoints couldn't be tested with a regular request anymore. Each one needed a two part test, the same request with no authorization header, which should come back 401, then with a valid bearer token, which should succeed. An endpoint that hands over data whether or not there's a token isn't actually protected, and the only way to prove the middleware is doing its job is to watch it fail. Testing also gets more stateful once tokens are involved, since they expire after an hour, so a request that worked earlier can start failing for reasons that have nothing to do with your code. I got in the habit of hitting /api/login for a fresh token before testing anything protected, which saved me from chasing problems that weren't there.
